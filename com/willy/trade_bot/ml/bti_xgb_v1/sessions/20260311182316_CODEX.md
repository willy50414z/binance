# CODEX Review - 20260311182316

## Review Scope

- Reviewed source note: `20260311182156_GEMINI.md`
- Review angle: leakage / correctness risk, validation risk, trading applicability risk, and actionability of the proposed plan

## Overall Judgment

這份計畫的主方向是對的，尤其是先把問題定義成「模型沒有學到可交易訊號」，而不是急著堆超參數，這個判斷合理。

但我不同意直接把 `total_trades >= 5` 放寬到 `>= 1` 當成主要診斷手段。這樣可以幫你看到候選門檻是否存在，但不能作為 threshold 選擇依據，否則很容易把純噪音誤判成有效訊號。

## 1. Leakage Or Correctness Risk

- `val_earlystop` 與 `val_cal` 合併可以增加樣本，但會把「模型選擇」與「機率校準」耦合在同一批資料上。這在小樣本下雖然實務上可接受作為暫時診斷，但要明確標記為 `diagnostic mode`，不能直接當成正式報表。
- 若接下來真的要掃 `lookahead=8/12`，`gap` 不能再維持固定直覺值；至少要重新檢查是否滿足 `gap >= lookahead + max_feature_lag`。否則你在擴張視界時，purge/embargo 可能不再足夠。
- 單純降低 ATR multiplier 來提高 label density 有研究價值，但必須同時輸出三件事：label class ratio、平均 barrier 寬度、以及 first-touch 命中率。否則你只會知道標籤變多，不知道標籤是否變得更雜訊。
- 目前建議補 `Feature Importance` 是正確的，但對 XGBoost 更應優先補 `prediction distribution by class` 與 `top-k feature gain / split`。如果重要特徵集中在少數價格衍生欄位，後面要再追查是否只是 regime proxy，而不是真正有穩定預測力的結構。

## 2. Validation Risk

- 目前最大風險不是 threshold 太嚴，而是 validation pipeline 沒有把「沒有 valid candidate」和「candidate 很差」分開呈現。這兩種狀況在研究意義上完全不同，報表必須顯式輸出：
  - threshold candidate count
  - fallback 是否觸發
  - fallback 前最佳候選的 precision / recall / expectancy / trade count
- `best_iteration = 4` 比較像 validation noise 或 feature-label mismatch，不太像單純 learning rate 問題。因此我不建議把 `learning_rate=0.01` 放在高優先。先補診斷，再決定是否需要調模型容量。
- 若 raw probabilities 長期塌在 `0.33` 左右，先比較 `raw vs sigmoid vs isotonic` 的 ranking 指標，而不是只看 calibrated probability 漂不漂亮。你要先確認模型有沒有排序能力，再談 calibration。
- 如果要放寬 `total_trades` 門檻，建議拆成兩層：
  - 診斷層：允許 `>= 1`，只為了看候選是否存在
  - 決策層：正式 threshold selection 仍維持較高下限，例如 `>= 5` 或 coverage 下限

## 3. Trading Applicability Risk

- 我同意你把問題歸因到 signal starvation，但還要補一個更交易導向的檢查：`predicted edge after cost`。如果即使放寬 threshold 後有訊號，但訊號的平均幅度仍低於費用加滑價，研究方向就應該回到標籤與特徵，不是 threshold。
- `lookahead` 拉長到 8 或 12 有機會提升可學性，但也會帶來兩個副作用：
  - 訊號頻率下降
  - 標籤和實際交易持有期偏離
  所以每次掃描都應一併輸出平均持有期、交易數、與 after-cost expectancy，否則很難判斷是否只是把問題往低頻移動。
- 如果你後面真的採用較低 threshold 下限，正式評估一定要加入 turnover、交易成本、最大連續虧損，不然很容易得到一個表面可交易、實際不可部署的策略。

## 4. Added Recommendations

### Higher-Priority Than Current Plan

1. 先補完整 diagnosis report，再做大幅參數掃描。
2. 在 `find_best_thresholds` 報表中區分 `no candidate`, `fallback`, `selected threshold` 三種狀態。
3. 補 `raw / sigmoid / isotonic` 的 ranking comparison，確認 calibration 是否真的有幫助。
4. 輸出每個 split 的 label density、prediction density、candidate count、best_iteration。

### Reasonable Next Experiments

1. 掃 `lookahead` 與 `atr_multiplier` 的二維組合，不要只單改其中一個。
2. 保留正式 threshold 下限，同時另外開一個診斷模式觀察 `>= 1` 的候選分布。
3. 若 `0.33` collapse 持續存在，再回頭檢查 feature set 是否缺少更長週期的 regime/context 特徵。

## 6. Recommended Final Plan

1. 先補診斷輸出：`candidate_count`、`fallback_used`、各類別機率分布、`max_prob` 均值/標準差、`best_iteration`、label density。
2. 將 threshold 搜尋拆成「診斷模式」與「正式選擇模式」，避免 `>= 1` 的結果直接污染正式決策。
3. 做 `lookahead x atr_multiplier` 小型 grid，而不是只單點測 `lookahead=8/12`。
4. 比較 `raw / sigmoid / isotonic` 的 ranking 與 calibration 指標；若 raw ranking 本身就差，先不要花太多力氣在 calibration。
5. 若診斷後仍顯示 ranking power 很弱，再考慮調 learning rate、模型容量，或回頭重整 feature set。

## Bottom Line

我同意原計畫想先處理 signal starvation，也同意先做診斷再談大改方向；但我不同意把放寬最低交易數直接視為 threshold 修正方案。那應該只是一個研究用探針，不是正式決策規則。
